### 제13판(`docs/es2022`) 대비 제17판(`docs/es2026`) 신규 문법 생성규칙 전수 차분 결과

 두 오프라인 HTML 규격서의 모든 `<emu-production name="...">` 선언을 차분 비교한 결과, 제14~17판에서 추가된 문법 비단말은 다음 **5개 영역**뿐임을 확인했다(누락 없음):

1. **Hashbang 주석 (ES2023, §12.5)**: `HashbangComment`, `InputElementHashbangOrRegExp`
2. **Import Attributes (ES2025, §16.2.2)**: `WithClause`, `WithEntries`, `AttributeKey`
3. **정규식 `v` 플래그 집합 표기·문자열 대안 (ES2024, §22.2.1)**: `ClassSetExpression`, `ClassUnion`, `ClassIntersection`, `ClassSubtraction`, `ClassSetRange`, `ClassSetOperand`, `NestedClass`, `ClassSetCharacter`, `ClassSetReservedDoublePunctuator`, `ClassSetReservedPunctuator`, `ClassSetSyntaxCharacter`, `ClassStringDisjunction`, `ClassStringDisjunctionContents`, `ClassString`
4. **정규식 인라인 패턴 수정자 (ES2025, §22.2.1)**: `RegularExpressionModifiers`, `RegularExpressionModifier`
5. **시간대 오프셋 문자열 문법 (ES2026, §21.4.1.33·부속서 A.7)**: `UTCOffset`, `ASCIISign`, `Hour`, `HourSubcomponents`, `TimeSeparator`, `MinuteSecond`, `TemporalDecimalFraction`, `TemporalDecimalSeparator` *(참고: `TemporalDecimalFraction`이라는 비단말 이름만 시간대 오프셋 소수 초 표기에 도입되었으며, `Temporal` 전역 객체 자체는 제17판 본문에 포함되지 않은 차기 제안이다.)*

## 4. 국제화 API(`ECMA-402 Intl`) 조건부 적합성 정책 확정 (`EXC-16`)

### 4.1 규격 근거 (ECMA-262 17th edition, §2 Conformance)

`docs/es2026/ECMAScript® 2026 Language Specification.html` 2절 Conformance(433~438행)는 국제화 API에 대해 다음과 같이 규정한다:

> *"A conforming implementation of ECMAScript **that provides** an application programming interface (API) that supports programs that need to adapt to the linguistic and cultural conventions used by different human languages and countries must implement the interface defined by the most recent edition of ECMA-402 that is compatible with this specification."*

즉, ECMA-262 적합성에서 `ECMA-402`(`globalThis.Intl`)는 **제공 여부가 조건부(conditional)**이다.
- `globalThis.Intl`을 제공하지 않는 구현은 ECMA-262 제17판 본문의 비-ECMA-402 `toLocaleString` / `localeCompare` 정의를 따르면 **완전한 적합(conforming) 구현**이다.
- 반대로 불완전한 부분 `Intl` 스텁만 노출하면 §2("제공하는 경우 최신 ECMA-402를 구현해야 함")를 위반하고 웹 스크립트의 기능 탐지(`typeof Intl !== 'undefined'`)까지 오작동시킨다.

### 4.2 기술적 근거 (JRE 6 호환성·외부 라이브러리 금지·JAR 용량)

1. **JRE 6 공개 API 한계**: Java 6(`java.util.Locale`, `Collator`, `DateFormat`, `NumberFormat`)에는 BCP 47 언어 태그 해석기(`Locale.forLanguageTag`는 Java 7 도입), IANA 시간대/달력 체계(`java.time`은 Java 8 도입), 복수형 규칙(`PluralRules`), 상대 시간(`RelativeTimeFormat`), 목록 형식(`ListFormat`), 문자소/단어/문장 분할(`Segmenter`), 표시 이름(`DisplayNames`) API와 데이터가 전혀 없다.
2. **외부 라이브러리 금지 및 JAR 크기 제약**: ICU4J 등 외부 라이브러리는 프로젝트 규칙상 사용할 수 없으며, 최신 ECMA-402 전체를 순수 Java로 구현하려면 수십 MB 규모의 CLDR 로케일·달력·정렬·분할 데이터 번들이 필요해 현재 약 1.1 MB인 `swingwebpanel-js.jar` 크기가 수십 배로 비대화된다(앞서 `EXC-12` 하이픈 사전 미번들, `EXC-15` Emoji 표 제외와 동일한 기준).

### 4.3 확정 정책 (`EXC-16`)

1. **`globalThis.Intl`은 노출하지 않는다** (`typeof globalThis.Intl === "undefined"`, `docs/FEATURE_MATRIX.md` 3절 `EXC-16` 등록).
2. 대신 ECMA-262 제17판 본문이 ECMA-402 미포함 구현에 요구하는 다음 기본 메서드의 규격 의미를 엄격히 준수하고 `P29-10`에서 검증한다:
   - `Object.prototype.toLocaleString()` (§20.1.3.5): `Invoke(this, "toString")` 호출
   - `Number.prototype.toLocaleString([reserved1 [, reserved2]])` (§21.1.3.4): `thisNumberValue` 검증 후 숫자 문자열 반환
   - `BigInt.prototype.toLocaleString([reserved1 [, reserved2]])` (§21.2.3.2): `thisBigIntValue` 검증 후 문자열 반환
   - `Date.prototype.toLocaleString` / `toLocaleDateString` / `toLocaleTimeString` (§21.4.4.39~41): `thisTimeValue` 검증(`NaN`이면 `"Invalid Date"`), 유한 시간값 문자열 반환
   - `String.prototype.localeCompare(that [, reserved1 [, reserved2]])` (§22.1.3.12, 부속서 F): `RequireObjectCoercible(this)`, `ToString(that)`, **유니코드 정준 동치(NFC 정규화 동등 문자열 비교 시 `0` 반환)** 보장(현행 엔진 실측 `'\u00E9'.localeCompare('e\u0301') === 0` 확인됨)
   - `Array.prototype.toLocaleString([reserved1 [, reserved2]])` (§23.1.3.31) 및 `%TypedArray%.prototype.toLocaleString` (§23.2.3.32): `null`/`undefined` 원소는 빈 문자열, 나머지 원소는 각 원소의 `Invoke(element, "toLocaleString")` 결과를 구분자로 결합
