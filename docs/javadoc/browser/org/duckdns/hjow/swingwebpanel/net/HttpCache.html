org.duckdns.hjow.swingwebpanel.net
Class HttpCache

java.lang.Object
  org.duckdns.hjow.swingwebpanel.net.HttpCache

public final class HttpCache
extends java.lang.Object

The HTTP cache of one browser component (plan items P19-03 to P19-06), a private cache in the sense of RFC 9111: it keeps successful GET responses of the main document and of sub-resources in memory, answers repeated requests without contacting the server while they are fresh, revalidates stale copies with a conditional request (If-None-Match, If-Modified-Since) and merges the headers of a 304 Not Modified into the stored copy, so a 304 never shows up as an empty page. Every component has its own cache object, so responses are never shared between components; the cache holds no reference to a component.

Rules (summary): only GET responses with status 200, 203, 204, 300, 404, 405, 410, 414 or 501 that arrive without redirect, without failure, in memory (not streamed) and below the entry size limit are stored; Cache-Control: no-store, Vary: * and Vary: Cookie prevent storing; Set-Cookie headers are never stored (cookies are handled once, when the response arrives). Freshness comes from max-age, then Expires, then the heuristic of 10 % of the time since Last-Modified (at most 24 hours); no-cache always revalidates; Vary selects the stored variant by the request headers that this layer controls (User-Agent, extra headers, Referer). A successful unsafe request (POST, PUT, DELETE, PATCH) removes the stored copies of its URL and of the URLs in Location and Content-Location. Request modes: ResourceRequest.CacheMode.DEFAULT follows the rules above, ResourceRequest.CacheMode.FORCE_RELOAD skips the stored copy and replaces it with the new response, ResourceRequest.CacheMode.PREFER_CACHE (history navigation) uses a stored copy even when it is stale. A response that was reached through a redirect is not stored because the redirect response itself is not visible here. Capacity is limited in bytes with least-recently-used eviction; a copy that a response object already returned stays valid after eviction.

브라우저 컴포넌트 하나의 HTTP 캐시(계획 P19-03~P19-06)로 RFC 9111 의 사설 캐시에 해당한다. 주 문서와 하위 리소스의 성공한 GET 응답을 메모리에 보관하고, 신선한 동안에는 서버에 접속하지 않고 같은 요청에 답하며, 오래된 사본은 조건부 요청(If-None-Match, If-Modified-Since)으로 재검증하고 304 Not Modified 의 헤더를 저장본에 합치므로 304 가 빈 페이지로 보이지 않는다. 컴포넌트마다 자신의 캐시 객체를 가지므로 응답이 컴포넌트 사이에 공유되지 않으며, 캐시는 컴포넌트를 참조하지 않는다.

규칙(요약): 리디렉션/실패/스트리밍 없이 메모리로 도착했고 항목 크기 제한 이하인 상태 200, 203, 204, 300, 404, 405, 410, 414, 501 의 GET 응답만 저장한다. Cache-Control: no-store, Vary: *, Vary: Cookie 는 저장을 막고 Set-Cookie 헤더는 저장하지 않는다(쿠키는 응답이 도착할 때 한 번만 처리). 신선도는 max-age, Expires, Last-Modified 이후 시간의 10 %(최대 24시간) 휴리스틱 순으로 정한다. no-cache 는 항상 재검증하고 Vary 는 이 계층이 제어하는 요청 헤더(User-Agent, 추가 헤더, Referer)로 저장된 변형을 고른다. 성공한 안전하지 않은 요청(POST, PUT, DELETE, PATCH)은 그 URL 과 Location/Content-Location 의 URL 의 저장본을 지운다. 요청 모드: ResourceRequest.CacheMode.DEFAULT 는 위 규칙, ResourceRequest.CacheMode.FORCE_RELOAD 는 저장본을 건너뛰고 새 응답으로 바꾸며, ResourceRequest.CacheMode.PREFER_CACHE (이력 이동)는 오래된 저장본도 쓴다. 리디렉션을 거친 응답은 리디렉션 응답 자체가 보이지 않으므로 저장하지 않는다. 용량은 바이트로 제한하며 가장 오래 쓰지 않은 항목부터 제거한다. 이미 응답 객체가 돌려준 사본은 제거된 뒤에도 유효하다.

Use: fetcher.setCache(new HttpCache()); the ResourceFetcher then consults the cache for every http/https GET.
