Class ScriptProcessorNode

java.lang.Object
  org.duckdns.hjow.swingwebpanel.media.webaudio.AudioNode
      org.duckdns.hjow.swingwebpanel.media.webaudio.ScriptProcessorNode

public final class ScriptProcessorNode
extends AudioNode

The deprecated node that lets a script generate or process audio directly (Web Audio API 1.0, 1.29 ScriptProcessorNode and 1.12 AudioProcessingEvent), implemented for old pages. The class is pure Java: it collects the input in blocks of bufferSize frames, asks the control side (through the BaseAudioContext.TaskSink of the context, the event loop of the page) to run a ScriptProcessorNode.ProcessListener for each block, and plays what the listener wrote into the output buffer one block later.

  • Blocks and delay. The input of block k (frames kB .. (k+1)B-1) is complete at the end of the block, when the event for it is requested. The listener has one whole block of time to answer; the output that it wrote is played during block k+2. So the audio is delayed by 2 bufferSize frames, like the double buffering of Chromium (the output of the first two blocks is silent). The playbackTime of the event is the context time at which the output buffer starts to play, (kB + 2B) / sampleRate. A single block of delay would require the listener to answer before the next quantum is rendered, which a listener on another thread can never do.
  • Real-time and offline. In a real-time context a listener that is late (it has not returned when its output is due) is abandoned: that block of output is silent and the late result is dropped (getLateBlockCount()); a listener that did not start yet is not run at all. In an offline context there is no real time to keep, so the rendering waits for the listener (at most RESPONSE_TIMEOUT_MILLIS milliseconds, which is then a late block): the result is the same on every run. The wait must not happen on the thread that runs the listener (the rendering thread of an offline context is not that thread).
  • The listener receives an input buffer (a copy of the block, valid only during the call) and an output buffer (silent at first); what the listener leaves in the output buffer when it returns is played. It runs on the control side if the context has a task sink, on the rendering thread if not. An exception of the listener is caught; the output stays as the listener left it (getLastListenerError()). Without a listener the output is silent and no event is requested.
  • Activity. The node is processed only while it has an input or an output connection (the specification: it is actively processing then), whether or not the other side is connected, so a generator without an input works. Becoming inactive (disconnected) forgets the block in progress and the pending output. The node stays in the context for as long as the context lives.
  • Channels. numberOfInputChannels and numberOfOutputChannels are from 0 to 32 (not both 0). The input is mixed to numberOfInputChannels channels (channelCount, mode explicit, which cannot be changed, as in the browsers an InvalidStateError where the specification says NotSupportedError). With 0 input channels the input is ignored and the input buffer of the event is null; with 0 output channels the output is a silent channel and the output buffer is null.
  • Memory. The node keeps three blocks (an input and an output buffer each) and creates at most 8 while the listener is slow; if all are in use the input of that block is dropped (getDroppedBlockCount()) and no event is requested.

스크립트가 오디오를 직접 만들거나 처리하게 하는 폐기 예정 노드(Web Audio API 1.0, 1.29 ScriptProcessorNode 와 1.12 AudioProcessingEvent)를 옛 페이지를 위해 구현한 것이다. 클래스는 순수 Java 이다: 입력을 bufferSize 프레임의 블록으로 모으고, 블록마다 컨텍스트의 BaseAudioContext.TaskSink(페이지의 이벤트 루프)를 통해 제어 쪽에 ScriptProcessorNode.ProcessListener 실행을 요청하고, 리스너가 출력 버퍼에 쓴 것을 한 블록 뒤에 재생한다.

  • 블록과 지연. 블록 k(프레임 kB .. (k+1)B-1)의 입력은 블록이 끝날 때 완성되며 그때 그 이벤트를 요청한다. 리스너에게는 블록 하나만큼의 시간이 응답 시간으로 주어지고, 리스너가 쓴 출력은 블록 k+2 동안 재생된다. 그래서 오디오는 2 bufferSize 프레임 지연되며 Chromium 의 이중 버퍼링과 같다(처음 두 블록의 출력은 무음). 이벤트의 playbackTime 은 출력 버퍼가 재생되기 시작하는 컨텍스트 시간 (kB + 2B) / sampleRate 이다. 지연이 한 블록이라면 다음 quantum 을 렌더링하기 전에 리스너가 응답해야 하는데, 다른 스레드의 리스너는 그럴 수 없다.
  • 실시간과 오프라인. 실시간 컨텍스트에서는 늦은 리스너(출력이 필요한 때까지 돌아오지 않음)를 포기한다: 그 블록의 출력은 무음이고 늦은 결과는 버려지며 (getLateBlockCount()), 아직 시작하지 않은 리스너는 실행되지 않는다. 오프라인 컨텍스트에는 지켜야 할 실시간이 없으므로 렌더링이 리스너를 기다린다 (최대 RESPONSE_TIMEOUT_MILLIS 밀리초이며, 넘으면 늦은 블록이다). 결과는 실행할 때마다 같다. 기다림이 리스너를 실행하는 스레드에서 일어나면 안 된다(오프라인 컨텍스트의 렌더링 스레드는 그 스레드가 아니다).
  • 리스너는 입력 버퍼(블록의 복사본이며 호출 동안만 유효)와 출력 버퍼(처음에는 무음)를 받으며, 리스너가 돌아올 때 출력 버퍼에 남긴 것이 재생된다. 컨텍스트에 작업 싱크가 있으면 제어 쪽에서, 없으면 렌더링 스레드에서 실행된다. 리스너의 예외는 잡는다. 출력은 리스너가 남긴 대로이다(getLastListenerError()). 리스너가 없으면 출력은 무음이고 이벤트를 요청하지 않는다.
  • 활성. 노드는 입력이나 출력 연결이 있는 동안에만 처리된다(규격: 그때 활성으로 처리한다). 반대쪽이 연결되어 있는지는 상관없으므로 입력 없는 생성기도 동작한다. 비활성이 되면(연결이 끊기면) 진행 중인 블록과 대기 중인 출력을 잊는다. 노드는 컨텍스트가 사는 동안 컨텍스트에 남는다.
  • 채널. numberOfInputChannels 와 numberOfOutputChannels 는 0 ~ 32 이다(둘 다 0 은 안 된다). 입력은 numberOfInputChannels 채널로 섞이며(channelCount, 모드 explicit, 바꿀 수 없다. 규격은 NotSupportedError 라 하지만 브라우저처럼 InvalidStateError), 입력 채널이 0 이면 입력을 무시하고 이벤트의 입력 버퍼는 null 이다. 출력 채널이 0 이면 출력은 무음 채널 하나이고 출력 버퍼는 null 이다.
  • 메모리. 노드는 블록 셋(각각 입력과 출력 버퍼)을 두고 리스너가 느릴 때 최대 8 개까지 만든다. 모두 쓰고 있으면 그 블록의 입력을 버리고 (getDroppedBlockCount()) 이벤트를 요청하지 않는다.
