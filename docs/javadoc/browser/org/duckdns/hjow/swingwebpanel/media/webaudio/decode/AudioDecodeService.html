org.duckdns.hjow.swingwebpanel.media.webaudio.decode
Class AudioDecodeService

java.lang.Object
  org.duckdns.hjow.swingwebpanel.media.webaudio.decode.AudioDecodeService

public final class AudioDecodeService
extends java.lang.Object

The background decoder behind decodeAudioData (plan item P25-05): a request carries the bytes of an audio file, the sample rate of the context and a DecodeCallback; the service decodes it on one of its own threads with AudioBufferDecoder (so neither the control thread, the rendering thread nor the event dispatch thread ever waits for a decoding, the "decoding thread" of the specification) and reports the result to the callback. The script layer builds on it: it detaches the ArrayBuffer, hands over its bytes, passes an executor that moves the callback to the document queue and settles the promise in the callback.

Threads. The service owns a small pool (DEFAULT_THREADS threads by default) of daemon threads named swingwebpanel-audio-decode-N that are created when needed and end after IDLE_MILLIS without work, so an unused or forgotten service holds no thread. There is no static state: every service is independent (one per context is the intended use).

Callbacks and order. The callback runs on the executor given with the request (the decoding thread if there is none) after the result is known. With one thread the requests are decoded and reported in the order in which they were made; with more threads they are decoded in parallel and may be reported in any order (a short sound need not wait for a long one; the specification says that multiple decoding threads can service calls in parallel and does not order the results). Each callback is called exactly once, or never if the request was cancelled. After a request returned from DecodeRequest.cancel() with true or after close() no callback of it is started, even if its result was already waiting in the executor.

Limits. At most MAX_PENDING_REQUESTS requests that have not finished decoding and at most MAX_PENDING_BYTES bytes of their data may be held at a time; decode(byte[], java.lang.String, float, org.duckdns.hjow.swingwebpanel.media.webaudio.decode.DecodeCallback, java.util.concurrent.Executor) throws NotSupportedError for the one that does not fit (the script layer rejects the promise with it). The service takes the array of a request over: the caller must not change it afterwards. The array is released as soon as the decoding is over.

Closing. close() (called when the context is closed, the page is left or the component is disposed) cancels every request silently (the running decodings are interrupted and end at their next block), refuses new ones with InvalidStateError and shuts the pool down. It is idempotent.

decodeAudioData 뒤의 백그라운드 디코더(계획 P25-05). 요청은 오디오 파일의 바이트, 컨텍스트의 표본율, DecodeCallback 을 가진다. 서비스는 자기 스레드에서 AudioBufferDecoder 로 디코딩하고(그래서 제어 스레드, 렌더링 스레드, 이벤트 디스패치 스레드는 디코딩을 기다리지 않는다. 규격의 "디코딩 스레드") 결과를 콜백에 알린다. 스크립트 계층은 이 위에 만든다. ArrayBuffer 를 분리하고 바이트를 넘기며, 콜백을 문서 큐로 옮기는 실행기를 주고, 콜백에서 promise 를 정산한다.

스레드. 서비스는 작은 풀(DEFAULT_THREADS 개가 기본)을 가지며 스레드는 swingwebpanel-audio-decode-N 이라는 이름의 데몬 스레드이다. 필요할 때 만들고 IDLE_MILLIS 동안 일이 없으면 끝나므로 쓰지 않거나 잊어버린 서비스도 스레드를 쥐고 있지 않는다. 정적 상태는 없다. 서비스마다 독립이다(컨텍스트마다 하나가 의도된 사용법).

콜백과 순서. 콜백은 결과가 나온 뒤 요청과 함께 준 실행기에서(없으면 디코딩 스레드에서) 실행된다. 스레드가 하나이면 요청한 순서대로 디코딩하고 알린다. 스레드가 더 많으면 병렬로 디코딩하며 어떤 순서로든 알릴 수 있다(짧은 소리가 긴 소리를 기다릴 필요가 없다. 규격은 여러 디코딩 스레드가 호출을 병렬로 처리할 수 있다고 하며 결과의 순서는 정하지 않는다). 콜백은 정확히 한 번 불리며 요청이 취소되었으면 불리지 않는다. 요청이 DecodeRequest.cancel() 에서 true 를 반환한 뒤나 close() 뒤에는 결과가 이미 실행기에서 기다리고 있었더라도 그 요청의 콜백이 시작되지 않는다.

한도. 디코딩이 끝나지 않은 요청은 MAX_PENDING_REQUESTS 개, 그 데이터는 MAX_PENDING_BYTES 바이트까지만 한 번에 들고 있는다. 들어가지 않는 요청은 decode(byte[], java.lang.String, float, org.duckdns.hjow.swingwebpanel.media.webaudio.decode.DecodeCallback, java.util.concurrent.Executor) 가 NotSupportedError 를 던진다(스크립트 계층이 그것으로 promise 를 거부한다). 서비스는 요청의 배열을 넘겨받는다. 호출한 쪽은 그 뒤에 바꾸면 안 된다. 배열은 디코딩이 끝나는 즉시 놓는다.

닫기. close()(컨텍스트를 닫거나 페이지를 떠나거나 컴포넌트를 폐기할 때 부른다)는 모든 요청을 조용히 취소하고(실행 중인 디코딩은 인터럽트되어 다음 블록에서 끝난다) 새 요청은 InvalidStateError 로 거부하며 풀을 종료한다. 여러 번 불러도 안전하다.
