Class WorkletScope

java.lang.Object
  org.duckdns.hjow.swingwebpanel.js.host.webaudio.worklet.WorkletScope

public final class WorkletScope
extends java.lang.Object

The AudioWorkletGlobalScope of one audio context and everything that runs in it (Web Audio API 1.0, 1.32; HTML Worklets): a script realm of its own with the built-in objects of ECMAScript 2015, the channel messaging and registerProcessor() (see WorkletGlobals), but no DOM and no window; it loads ES2015 modules for audioWorklet.addModule(), creates the AudioWorkletProcessor instance of every AudioWorkletNode and calls its process() method in every render quantum.

Threads, and who may touch the realm. A script realm belongs to one thread at a time, so every use of the realm of this scope holds lock (a fair lock). Three kinds of code take it:

  • the worklet thread (swingwebpanel-audio-worklet-N, a daemon thread that starts with the first addModule() and ends with the scope): it evaluates modules and runs the realm tasks (the delivery of a message to a port of a processor). It fetches modules without the lock (ModuleGraphFetcher), so a slow network never delays the rendering thread;
  • the rendering thread of the audio context: it constructs the processors (a control message at the start of a quantum, so that the result is the same on every run of an offline context) and calls process() once per node per quantum. This is where the specification wants the script to run. In a real-time context it only tries the lock for WorkletLimits.REALTIME_LOCK_WAIT_MILLIS ms: if the worklet thread is busy the node is silent for that quantum (AudioWorkletNode.SKIPPED) and the other nodes of that quantum do not wait at all. A real-time context therefore never waits for a script that is not its processor for long; an offline context has no deadline, waits for the lock and, before it processes a quantum, runs the pending realm tasks itself, so that a message posted before startRendering() (or before a quantum) is delivered before that quantum, deterministically;
  • nobody else: the page never touches the realm. What the page needs reaches it as plain data (names, descriptors, serialized messages) through task queues.
A call of process() has a limit of WorkletLimits.PROCESS_STEP_LIMIT steps and, in a real-time context, WorkletLimits.REALTIME_PROCESS_TIME_LIMIT_MILLIS ms; a processor that exceeds it fails like a processor that throws (processorerror, silence for good). dispose() (the context was closed, the page was replaced, scripts were switched off) cancels the running script, drops the queues and ends the worklet thread without waiting; the nodes of the scope are silent from then on.

오디오 컨텍스트 하나의 AudioWorkletGlobalScope 와 그 안에서 실행되는 모든 것(Web Audio API 1.0, 1.32. HTML Worklets): ECMAScript 2015 의 내장 객체, 채널 메시징, registerProcessor()(WorkletGlobals 참고)가 있지만 DOM 도 window 도 없는 자기만의 스크립트 realm 이다. audioWorklet.addModule() 를 위해 ES2015 모듈을 불러오고, AudioWorkletNode 마다 AudioWorkletProcessor 인스턴스를 만들고, render quantum 마다 그 process() 메서드를 호출한다.

스레드와 realm 을 만질 수 있는 쪽. 스크립트 realm 은 한 번에 한 스레드의 것이므로 이 스코프의 realm 을 쓰는 모든 코드는 lock(공정한 잠금)을 쥔다. 세 종류의 코드가 쥔다:

  • worklet 스레드(swingwebpanel-audio-worklet-N, 첫 addModule() 에 시작해 스코프와 함께 끝나는 데몬 스레드): 모듈을 평가하고 realm 작업(프로세서 포트로의 메시지 전달)을 실행한다. 모듈은 잠금 없이 가져오므로(ModuleGraphFetcher) 느린 네트워크가 렌더링 스레드를 늦추지 않는다.
  • 오디오 컨텍스트의 렌더링 스레드: 프로세서를 만들고(quantum 시작의 제어 메시지이므로 오프라인 컨텍스트의 결과는 실행할 때마다 같다) 노드마다 quantum 마다 한 번 process() 를 호출한다. 규격이 스크립트가 실행되기를 바라는 곳이 여기이다. 실시간 컨텍스트에서는 잠금을 WorkletLimits.REALTIME_LOCK_WAIT_MILLIS ms 동안 시도만 한다: worklet 스레드가 바쁘면 노드는 그 quantum 에 무음이고(AudioWorkletNode.SKIPPED) 같은 quantum 의 다른 노드는 전혀 기다리지 않는다. 그러므로 실시간 컨텍스트는 자기 프로세서가 아닌 스크립트를 오래 기다리지 않는다. 오프라인 컨텍스트에는 기한이 없으므로 잠금을 기다리고, quantum 을 처리하기 전에 쌓인 realm 작업을 직접 실행하므로 startRendering() 전(또는 quantum 전)에 보낸 메시지는 그 quantum 전에 결정적으로 전달된다.
  • 그 밖에는 아무도 아니다: 페이지는 realm 을 만지지 않는다. 페이지에 필요한 것은 작업 큐를 거쳐 일반 데이터(이름, 설명, 직렬화된 메시지)로 닿는다.
process() 한 번의 호출은 WorkletLimits.PROCESS_STEP_LIMIT 단계, 실시간 컨텍스트에서는 WorkletLimits.REALTIME_PROCESS_TIME_LIMIT_MILLIS ms 의 한도가 있다. 넘는 프로세서는 예외를 던지는 프로세서처럼 실패한다(processorerror, 영구 무음). dispose()(컨텍스트가 닫혔거나, 페이지가 교체되었거나, 스크립트가 꺼졌다)는 실행 중인 스크립트를 취소하고, 큐를 비우고, 기다리지 않고 worklet 스레드를 끝낸다. 그 뒤 스코프의 노드는 무음이다.

addModule

public void addModule(java.lang.String moduleKey,
                      ModuleScriptSource.Credentials credentials,
                      WorkletScope.Completion done)
Loads a module and everything it imports into the global scope, evaluates it (registerProcessor() calls happen here) and tells the page how it ended. A module that the scope has loaded already is not loaded again (the call succeeds). Callable from any thread; the work is done by the worklet thread.

모듈과 그것이 import 하는 모든 것을 전역 범위에 불러와 평가하고(registerProcessor() 호출이 여기서 일어난다) 어떻게 끝났는지 페이지에 알린다. 스코프가 이미 불러온 모듈은 다시 불러오지 않는다(호출은 성공한다). 어느 스레드에서나 부를 수 있으며 일은 worklet 스레드가 한다.

dispose

public void dispose()
Ends the scope at once and from any thread without waiting: the script that runs is cancelled at its next step, the queues are dropped and the worklet thread ends. Nodes whose processors live in the scope are silent afterwards. Calling it again does nothing.

스코프를 기다리지 않고 어느 스레드에서나 즉시 끝낸다: 실행 중인 스크립트는 다음 단계에서 취소되고, 큐가 비워지며, worklet 스레드가 끝난다. 프로세서가 스코프에 있는 노드는 그 뒤 무음이다. 다시 불러도 아무 일도 없다.
